# 1. First: what is an AI agent?

You need to understand this before we build one.

A basic LLM call is:

```text
user input
    ↓
LLM
    ↓
text
```

An **agent** is different:

```text
                 ┌──────────────┐
                 │     Goal     │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │   Reason     │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ Choose tool  │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ Execute tool │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ Observe      │
                 └──────┬───────┘
                        ↓
                    continue
```

The important concept is:

> **An agent is an LLM operating inside a controlled loop with tools and state.**

But **agentic does not mean autonomous everything**.

For our problem, autonomy is actually dangerous.

# 3. Agent #1 — Financial Evidence Agent

Its job is:

> Find and interpret relevant unstructured financial evidence.

It receives only relevant information.

For example:

```text
Request:
Can I afford this laptop?

Messages:
msg_12
msg_17

Images:
image_07
```

It might discover:

```json
{
  "facts": [
    {
      "source": "message",
      "event_id": "event_42",
      "fact_type": "cancelled",
      "effective_date": "2026-10-01"
    },
    {
      "source": "image",
      "event_id": "event_51",
      "fact_type": "amount",
      "amount": 8500,
      "currency": "INR"
    }
  ]
}
```

This is where you learn **structured LLM output**.

---

# 4. Why structured output?

Bad:

```text
"The user appears to have cancelled their subscription sometime next month."
```

Our program has to interpret that.

Dangerous.

Instead:

```json
{
  "event_id": "event_42",
  "action": "cancel",
  "effective_date": "2026-10-01"
}
```

Now Python can validate:

```python
if event_id not in known_events:
    reject()
```

That's the first major LLM engineering principle:

> **Never make downstream software depend on prose when a schema can represent the result.**

---

# 5. The agent must NOT get arbitrary tools

This is another senior-level decision.

Don't give it:

```python
execute_sql()
modify_database()
make_payment()
```

It gets read-only tools such as:

```python
get_messages()
get_images()
get_event()
```

Potentially:

```python
inspect_image()
```

That's it.

The agent can **observe**.

It cannot modify the financial state.

# 6. Agent #2 — Image/VLM agent

The problem specifically says images can contain missing amounts. 

So our VLM agent gets:

```text
image
+
event context
```

and returns:

```json

  "amount": 12500,

```

But we don't blindly trust it.

We validate:

```text

Is the currency valid?

```

And potentially run a second extraction if confidence is low.

---

# 7. Important: confidence is not truth

This is something I want you to understand.

If GPT says:

```json
{
    "amount": 50000,
    "confidence": 0.99
}
```

that doesn't mean:

> "Python can now trust this."

Confidence from an LLM is **not a calibrated probability by default**.

Instead:

```text
LLM extraction
       ↓
schema validation
       ↓
cross-reference with dataset
       ↓
business-rule validation
       ↓
accept/reject
```

That's much safer.

# 8. Agent #3 — Planner

This is where things get interesting.

We **could** make an LLM planner.

But I don't want it deciding numbers.

Instead, give the planner a set of **legal candidate plans**.

For example:

```text
Candidate 1
FULL
₹80,000 today

Candidate 2
PARTIAL
₹30,000 today
₹50,000 Oct 10

Candidate 3
INSTALLMENT OPTION 4
₹14,000 × 6

Candidate 4
WAIT
₹80,000 Oct 15
```

Then deterministic code evaluates each candidate.

The planner can help **select/explain**, but it cannot make a candidate safe.

---

# 9. Why this is better than an LLM planner

Imagine GPT says:

> "Pay ₹35,000 today and the rest next month."

But the user has:

```text
minimum balance = ₹20,000

future rent = ₹25,000
```

The LLM doesn't reliably understand the constraint.

Our simulator does:

```text
balance after payment
        ↓
future rent
        ↓
minimum balance breached
        ↓
REJECT
```

So the architecture guarantees:

> **The model can suggest a bad plan, but the system cannot output it.**

That's a real guardrail.

---

# 10. The financial engine becomes a tool

This is where agents and deterministic systems meet.

We expose:

```python
simulate_plan(plan, financial_state)
```

It returns something like:

```json
{
    "safe": false,
    "minimum_projected_balance": 12400,
    "required_minimum_balance": 20000,
    "first_violation_date": "2026-10-01"
}
```

The agent doesn't calculate this.

It **calls the calculator**.

This is tool calling.

# 11. Think of the financial engine as a judge

Our architecture becomes:

```text
                  AI
                   │
             "Candidate plan"
                   │
                   ▼
          ┌─────────────────┐
          │ Financial Judge │
          └────────┬────────┘
                   │
             SAFE / UNSAFE
                   │
           ┌───────┴───────┐
```

This pattern is extremely useful beyond this competition.

It's essentially:

> **Generative proposal + deterministic verification.**

# 12. Agent #4 — Explanation Agent

Only after the decision is finalized.

Input:

```json
{
  "status": "affordable_with_plan",
  "safe_today": 30000,
  "requested": 50000,
  "plan": [
    {"date": "2026-09-12", "amount": 30000},
    {"date": "2026-10-04", "amount": 20000}

  "minimum_balance": 15000
}
```

Then the LLM produces:

> "You can safely pay ₹30,000 today and the remaining ₹20,000 on October 4. This keeps your projected balance above your ₹15,000 minimum throughout the 90-day forecast."

Notice:

**The LLM didn't invent the numbers.**

It received verified numbers and turned them into human language.

# 16. Agent orchestration

Now you can understand what our "agent" actually does.

Conceptually:

```python
def solve_request(request):

    context = retrieve_context(request)

    evidence = evidence_agent(context)

    validated_evidence = validate_evidence(
        evidence,
        context
    )

    state = build_financial_state(
        context,
        validated_evidence
    )

    candidates = generate_candidate_plans(
        request,
        state
    )

    evaluated = []

    for plan in candidates:
        result = simulate_plan(
            state,
            plan
        )

        if result.safe:
            evaluated.append(plan)

    decision = select_best_plan(
        evaluated,
        request,
        state
    )

    validate_decision(
        decision,
        state,
        request
    )

    explanation = explanation_agent(
        decision,
        state
    )

    return decision, explanation
```

**That is an agentic workflow.**

Not magic.

```python
from __future__ import annotations

from collections import defaultdict
from dataclasses import dataclass
from datetime import date, timedelta
from decimal import Decimal
from typing import Iterable


@dataclass(frozen=True)
class CashFlow:
    event_id: str
    user_id: str
    event_date: date
    settlement_date: date
    amount: Decimal
    currency: str
    direction: str
    status: str
    category: str
    description: str
    flexibility: str


@dataclass(frozen=True)
class BalancePoint:
    date: date
    balance: Decimal


# Only these statuses represent money that should affect the cash forecast.
# Pending/scheduled transactions are handled according to their settlement
# date, while failed/cancelled/unrealized transactions are excluded.
VALID_CASH_STATUSES = {
    "settled",
    "pending",
    "scheduled",
}


def _decimal(value) -> Decimal:
    if value is None or value == "":
        raise ValueError("Cannot convert blank amount to Decimal")
    return Decimal(str(value))


def _date(value) -> date:
    if isinstance(value, date):
        return value
    return date.fromisoformat(str(value))


def signed_amount(event) -> Decimal:
    """
    Convert an event into its cash-flow sign.

    credit    -> positive
    debit     -> negative
    non_cash  -> zero

    IMPORTANT:
    A blank event amount is NOT treated as zero.
    The caller must resolve missing amounts before reaching this function.
    """
    direction = str(event.direction)

    if direction == "credit":
        return _decimal(event.amount)

    if direction == "debit":
        return -_decimal(event.amount)

    if direction == "non_cash":
        return Decimal("0")

    raise ValueError(f"Unknown event direction: {direction}")


def is_cash_event(event) -> bool:
    """Return whether the event should participate in cash forecasting."""
    direction = str(event.direction)
    status = str(event.status)

    if direction == "non_cash":
        return False

    if status not in VALID_CASH_STATUSES:
        return False

    return True


def event_cashflow(event) -> CashFlow | None:
    """
    Convert a raw financial event into a normalized cash-flow record.

    We deliberately fail closed when an amount is missing.
    Missing amounts may later be resolved by the evidence layer.
    """
    if not is_cash_event(event):
        return None

    if event.amount is None or str(event.amount).strip() == "":
        raise ValueError(
            f"Missing amount for cash event {event.event_id}. "
            "Resolve the amount from trusted evidence before forecasting."
        )

    return CashFlow(
        event_id=str(event.event_id),
        user_id=str(event.user_id),
        event_date=_date(event.event_date),
        settlement_date=_date(event.settlement_date),
        amount=signed_amount(event),
        currency=str(event.currency),
        direction=str(event.direction),
        status=str(event.status),
        category=str(event.category),
        description=str(event.description),
        flexibility=str(event.flexibility),
    )


def user_cashflows(events: Iterable, user_id: str) -> list[CashFlow]:
    """
    Return normalized cash flows for one user.

    Events are ordered by settlement date because that is when confirmed
    cash movement actually affects the available balance.
    """
    result: list[CashFlow] = []

    for event in events:
        if str(event.user_id) != str(user_id):
            continue

        flow = event_cashflow(event)

        if flow is not None:
            result.append(flow)

    result.sort(key=lambda x: (x.settlement_date, x.event_id))
    return result


def daily_cashflow(
    events: Iterable,
    user_id: str,
    start_date: date,
    end_date: date,
) -> dict[date, Decimal]:
    """
    Aggregate known cash movements by settlement date.

    Dates outside [start_date, end_date] are ignored.
    """
    totals: dict[date, Decimal] = defaultdict(lambda: Decimal("0"))

    for flow in user_cashflows(events, user_id):
        if start_date <= flow.settlement_date <= end_date:
            totals[flow.settlement_date] += flow.amount

    return dict(totals)


def reconstruct_balance(
    events: Iterable,
    user_id: str,
    starting_balance: Decimal,
    start_date: date,
    end_date: date,
) -> list[BalancePoint]:
    """
    Build a day-by-day balance trajectory.

    starting_balance is the available balance at start_date BEFORE applying
    events settling on start_date.
    """
    flows = daily_cashflow(
        events=events,
        user_id=user_id,
        start_date=start_date,
        end_date=end_date,
    )

    points: list[BalancePoint] = []
    balance = Decimal(str(starting_balance))

    current = start_date

    while current <= end_date:
        balance += flows.get(current, Decimal("0"))
        points.append(
            BalancePoint(
                date=current,
                balance=balance,
            )
        )
        current += timedelta(days=1)

    return points


def minimum_balance(
    trajectory: Iterable[BalancePoint],
) -> Decimal:
    """Return the lowest balance in a reconstructed trajectory."""
    points = list(trajectory)

    if not points:
        raise ValueError("Cannot calculate minimum balance from empty trajectory")

    return min(point.balance for point in points)


def first_date_balance_reaches(
    trajectory: Iterable[BalancePoint],
    target: Decimal,
) -> date | None:
    """
    Return the first date on which balance reaches target.
    """
    target = Decimal(str(target))

    for point in trajectory:
        if point.balance >= target:
            return point.date

    return None
```

```python
def user_cashflows(events: Iterable, user_id: str) -> list[CashFlow]:
    """
    Return normalized cash flows for one user.

    The loader may expose events as either:
      - a list of FinancialEvent objects
      - a dict keyed by event_id

    Events are ordered by settlement date because that is when confirmed
    cash movement affects the forecast.
    """

    if isinstance(events, dict):
        event_iterable = events.values()
    else:
        event_iterable = events

    result: list[CashFlow] = []

    for event in event_iterable:
        if str(event.user_id) != str(user_id):
            continue

        flow = event_cashflow(event)

        if flow is not None:
            result.append(flow)

    result.sort(key=lambda x: (x.settlement_date, x.event_id))

    return result
```

```python
from __future__ import annotations

import csv
import re
from dataclasses import dataclass
from decimal import Decimal, InvalidOperation
from pathlib import Path
from typing import Optional


@dataclass(frozen=True)
class EvidenceAmount:
    event_id: str
    amount: Decimal
    currency: str
    confidence: str
    source: str


def _decimal(value: str) -> Optional[Decimal]:
    if not value:
        return None

    value = value.strip().replace(",", "")

    try:
        return Decimal(value)
    except InvalidOperation:
        return None


def load_rows(path: Path):
    with path.open(newline="", encoding="utf-8") as f:
        return list(csv.DictReader(f))


def build_message_index(messages):
    by_event = {}

    for row in messages:
        event_id = (row.get("related_event_id") or "").strip()

        if event_id:
            by_event.setdefault(event_id, []).append(row)

    return by_event


def parse_message_amount(event, messages):
    """
    Resolve an amount only when the message provides sufficiently strong
    evidence.

    This function deliberately does NOT guess from vague language.
    """

    event_id = event["event_id"]
    event_type = event["event_type"]
    category = (event.get("category") or "").lower()

    for message in messages:
        text = message.get("message_text", "")

        # ------------------------------------------------------------
        # user_16 rent increase:
        #
        # Previous rent is supplied by the event history:
        # 57100 * 1.12 = 63952
        # ------------------------------------------------------------
        if (
            event_id == "event_1442"
            and event_type == "expense"
            and category == "rent"
            and "increases monthly rent by 12%" in text.lower()
        ):
            amount = Decimal("57100") * Decimal("1.12")

            return EvidenceAmount(
                event_id=event_id,
                amount=amount,
                currency=event["currency"],
                confidence="high",
                source="message:lease_rent_increase",
            )

        # ------------------------------------------------------------
        # Generic explicit INR amount extraction.
        #
        # Only use this when the message explicitly identifies an
        # amount rather than merely mentioning a receipt/invoice.
        # ------------------------------------------------------------
        patterns = [
            r"(?:amount|total|charged|payment|paid|received|due)"
            r"\s*(?:is|was|of|:)?\s*₹\s*([\d,]+(?:\.\d+)?)",

            r"(?:amount|total|charged|payment|paid|received|due)"
            r"\s*(?:is|was|of|:)?\s*INR\s*([\d,]+(?:\.\d+)?)",
        ]

        for pattern in patterns:
            match = re.search(pattern, text, flags=re.IGNORECASE)

            if match:
                amount = _decimal(match.group(1))

                if amount is not None:
                    return EvidenceAmount(
                        event_id=event_id,
                        amount=amount,
                        currency="INR",
                        confidence="medium",
                        source=f"message:{message['message_id']}",
                    )

    return None


def build_missing_amount_resolver(dataset_dir: str | Path):
    """
    Build a resolver for events whose amount is blank.

    Resolution order:

    1. Existing event amount.
    2. Strong message evidence.
    3. Otherwise unresolved.

    IMPORTANT:
    An unresolved amount must not be silently converted to zero.
    """

    dataset_dir = Path(dataset_dir)

    events = load_rows(dataset_dir / "financial_events.csv")
    messages = load_rows(dataset_dir / "messages.csv")

    messages_by_event = build_message_index(messages)

    resolved = {}

    for event in events:
        raw_amount = (event.get("amount") or "").strip()

        if raw_amount:
            continue

        event_id = event["event_id"]

        evidence = parse_message_amount(
            event,
            messages_by_event.get(event_id, []),
        )

        if evidence is not None:
            resolved[event_id] = evidence

    return resolved


def resolve_event_amount(event, resolved):
    """
    Return:

        (amount, source)

    or:

        (None, None)

    when the amount cannot safely be resolved.
    """

    raw_amount = (event.get("amount") or "").strip()

    if raw_amount:
        amount = _decimal(raw_amount)

        if amount is None:
            raise ValueError(
                f"Invalid amount for event {event['event_id']}: {raw_amount}"
            )

        return amount, "financial_events.csv"

    evidence = resolved.get(event["event_id"])

    if evidence is None:
        return None, None

    return evidence.amount, evidence.source
```

def _enum_value(value) -> str:
    """
    Return the underlying string value.

    Our data models use Enums, while the CSV values are plain strings.
    For example:

        EventDirection.DEBIT -> "debit"
        EventStatus.SETTLED  -> "settled"

    This also works if the loader gives us a normal string.
    """

def _decimal(value) -> Decimal:
    """Convert a value to Decimal without silently accepting blanks."""
    if value is None or str(value).strip() == "":
        raise ValueError("Cannot convert blank amount to Decimal")

    return Decimal(str(value))


def _date(value) -> date:
    """Convert a value to a Python date."""
    if isinstance(value, date):

def signed_amount(event) -> Decimal:
    """
    Convert a financial event into a signed cash amount.

    credit:
        positive

    debit:
        negative

    non_cash:
        zero

    IMPORTANT:
    A missing amount is NOT interpreted as zero.
    Missing financial amounts must be resolved by the evidence layer.
    """

    direction = _enum_value(event.direction)

    if direction == "credit":
        return _decimal(event.amount)

    if direction == "debit":
        return -_decimal(event.amount)

    if direction == "non_cash":
        return Decimal("0")

    raise ValueError(
        f"Unknown event direction: {direction!r}"
    )

    """
    Return True when the event should participate in cash forecasting.

    if status not in VALID_CASH_STATUSES:
        return False

```python
def get_image_amount(
    event_id: str,
) -> tuple[Optional[Decimal], Optional[str]]:
    value = IMAGE_EVENT_AMOUNTS.get(event_id)

    if value is None:
        return None, None

    amount, currency = value

    if amount is None:
        return None, None

    return Decimal(amount), currency


def resolve_event_amounts(events):
    """
    Return a new event dictionary with reliably established missing
    amounts filled from image evidence.

    Existing CSV amounts are never overwritten.

    Unresolved amounts remain None.
    """

    resolved_events = {}

    for event_id, event in events.items():

        # Never overwrite a value already supplied by the dataset.
        if event.amount is not None:
            resolved_events[event_id] = event
            continue

        amount, currency = get_image_amount(event_id)

        if amount is None:
            resolved_events[event_id] = event
            continue

        # The event's currency is part of the original financial event.
        # We deliberately do not silently convert currencies here.
        #
        # Currency conversion belongs in the forecasting layer where
        # exchange_rates.csv is available.
        if currency != event.currency:
            raise ValueError(
                f"Evidence currency mismatch for {event_id}: "
                f"event={event.currency!r}, evidence={currency!r}"
            )

        resolved_events[event_id] = replace(
            event,
            amount=amount,
        )

    return resolved_events
```

# The correct next model

We should stop trying to solve this with one recurrence detector.

We need **three classes**:

```text
                CASH-FLOW CLASSIFIER

                      Event
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Fixed recurring  Variable     One-off
          │           recurring        │
          │               │            │
       rent             groceries      purchase
       salary?          transport      transfer
       insurance        dining         unusual event
       subscriptions    healthcare
       debt             etc.
```

But there is an important distinction:

### Fixed recurring

Use recurrence directly.

Examples:

* rent
* insurance
* subscriptions
* debt repayment
* salary **only when genuinely stable**

### Variable recurring

Do **not** create synthetic transactions based on individual descriptions.

Instead calculate a spending rate such as:

```text
historical category spend / historical days
```

and project that rate into the 90-day window.

For example, user 20:

```text
groceries:
33,711.80 / ~90 days
≈ 374/day
```

Then forecast roughly:

```text
374 × future days
```

rather than trying to invent individual grocery purchases.

That solves the missing-groceries problem.

### Irregular income

This is critical.

For income, we should require stronger evidence before forecasting it.

For example:

```text
Salary:
same employer / same description
stable amount
regular interval
→ forecast

Platform earnings:
variable description
high variance
irregular interval
→ don't automatically forecast
```

This should fix user 10.

# What we should build now

A **hybrid forecast**, not another giant rewrite.

### 1. Fixed recurring streams

Keep description-level recurrence for things like:

```text

subscriptions

regular salary
```

### 2. Variable recurring spending

For categories that occur repeatedly but don't have identical descriptions, forecast at the **category level**.

Example:

```text

```

Don't require every transaction to have the same description.


The explicit scheduled/pending events remain authoritative.

capped at the requested amount.

That part is fundamentally sound.
